# Звіт з практичної роботи №1. Моделювання даних і вибір підходу

## 1. Опис предметної області: Електронний журнал коледжу
**Користувачі системи:**
*   **Викладачі:** виставляють оцінки, відмічають присутність, планують розклад занять.
*   **Студенти:** переглядають свої оцінки, розклад, домашні завдання.
*   **Адміністратори/Деканат:** керують списками груп, призначають викладачів на дисципліни, формують загальні звіти про успішність.

**Об'єкти предметної області:**
Студент, Викладач, Академічна група, Дисципліна, Заняття, Оцінка.

**Операції, що підтримуються:**
*   Додавання, редагування та видалення користувачів.
*   Реєстрація проведення заняття та виставлення оцінок.
*   Перегляд журналу конкретної групи з певної дисципліни.
*   Генерація звітів (наприклад, розрахунок середнього балу).

---

## 2. Списки фактів та прив'язка до об'єктів
*   **Об'єкт «Студент»:** ПІБ, номер студентського квитка, контактний email, дата народження.
*   **Об'єкт «Академічна група»:** Назва групи (напр. ІПЗ-31), курс, рік вступу, спеціальність.
*   **Об'єкт «Викладач»:** ПІБ, посада, кафедра.
*   **Об'єкт «Дисципліна»:** Назва предмета, кількість годин, тип контролю (іспит/залік).
*   **Об'єкт «Заняття»:** Дата, тема, тип (лекція/практика), аудиторія.
*   **Об'єкт «Оцінка»:** Значення балу, коментар викладача.

## 4. Порівняння підходів до моделювання даних

| Модель даних | Сильна сторона | Слабка сторона |
| :--- | :--- | :--- |
| **Ієрархічна** | Швидкий пошук зверху вниз. | Неможливо описати, що викладач веде заняття у багатьох групах. |
| **Мережева** | Вирішує проблему зв'язків "багато до багатьох". | Надзвичайно складна зміна структури. |
| **Реляційна** | Ідеально підходить для табличних даних. | Складні запити вимагають об'єднання багатьох таблиць. |
| **Об'єктна** | Структура бази збігається з класами в коді ООП. | Складніше інтегрувати з інструментами аналітики. |
| **Документна**| Гнучкість: можна зберігати "профіль" в одному документі. | Проблеми з узгодженістю при зміні спільних сутностей. |
| **Ключ-значення** | Максимальна швидкість читання. | Неможливо виконати складний пошук. |

## 5. Висновок (Обґрунтування вибору моделі даних)
Для системи «Електронний журнал коледжу» найкращим вибором є **реляційна модель даних**. Дані в цій предметній області мають чітко визначену, сувору структуру та постійні зв'язки. Реляційні СКБД забезпечують надійність, консистентність даних та виконання ACID-транзакцій, що є критично важливим для збереження оцінок. Наявність потужної мови SQL дозволить легко формувати звіти. Тому реляційний підхід залишається галузевим стандартом для таких систем.

## 6. Відповіді на питання для захисту
1. **Чим дані відрізняються від інформації та знань?**
   Дані — це сирі, необроблені факти. Інформація — це оброблені, структуровані дані з контекстом. Знання — це розуміння та висновки на основі інформації.
2. **Які функції СКБД вам знадобляться для обраної системи?**
   Керування доступом, забезпечення цілісності даних, резервне копіювання, підтримка транзакцій.
3. **Чому один і той самий факт може бути збережено з помилкою за кількома адресами?**
   Це відбувається через дублювання (надлишковість) даних у погано спроєктованих базах, що призводить до аномалій оновлення.
4. **Які критерії використали для вибору моделі даних?**
   Ступінь структурованості даних, необхідність підтримки зв'язків "багато-до-багатьох", вимоги до цілісності та консистентності.
